# Using the bootstrap flake

## Implemented scope

The root [flake.nix](../flake.nix) implements the tool sets selected in [bootstrap-tools.md](bootstrap-tools.md), for `x86_64-linux` only. [flake.lock](../flake.lock) pins the approved nixpkgs commit and its Nix-generated content hash. The only package override is Gawk with GMP/MPFR support.

This supplies bootstrap tools and checks. It does not implement recipe execution, dependency resolution, the Bubblewrap policy, system installation, or the KPB-owned glibc runtime. The bundles themselves depend on the Nix store and are build inputs, not final KPB packages.

| Output | Purpose |
|---|---|
| `packages.x86_64-linux.bootstrap-recipe-tools` | A `/bin` tree for the 18 selected recipe-tool entries. |
| `packages.x86_64-linux.bootstrap-orchestration-tools` | A `/bin` tree for orchestration tools and `/etc/ssl/certs/ca-bundle.crt`. |
| `packages.x86_64-linux.gawk-mpfr` | The explicit Gawk variant, with a required precision check during installation verification. |
| `checks.x86_64-linux.gawk-mpfr` | Functional high-precision arithmetic check on the installed Gawk. |
| `checks.x86_64-linux.bootstrap-layout` | Required executable and certificate paths, and absence of orchestration-only/undeclared tools from the recipe bundle's `/bin`. |

The two bundles expose `toolVersions` attributes for inspection. There is no default package or combined development shell: callers must choose the intended role explicitly. PATH grouping does not restrict execution of other binaries in a tool's runtime closure or create a sandbox.

## Requirements and commands

Nix, the `nix-command` and `flakes` features, and access to the store must already be available. These commands do not enable features or change Nix configuration, profiles, shell startup files, or the host's `/opt/kpb`. Builds may download dependencies, compile Gawk, and write to the Nix store/caches.

From a Git checkout where `flake.nix` and `flake.lock` are tracked, evaluate and run checks using the existing lock:

```sh
nix flake check --no-build --no-update-lock-file
nix flake check --no-update-lock-file --print-build-logs
```

Build either bundle without creating a `result` symlink or installing it into a profile:

```sh
nix build --no-update-lock-file --no-link --print-out-paths .#bootstrap-recipe-tools
nix build --no-update-lock-file --no-link --print-out-paths .#bootstrap-orchestration-tools
```

Inspect the selected versions without building the packages:

```sh
nix eval --json --no-update-lock-file .#packages.x86_64-linux.bootstrap-recipe-tools.toolVersions
nix eval --json --no-update-lock-file .#packages.x86_64-linux.bootstrap-orchestration-tools.toolVersions
```

If reviewing new, untracked flake files, Nix's Git source filtering may omit them. To evaluate the exact files without changing the Git index or including unrelated workspace contents, copy only the two flake files into a temporary directory:

```sh
kpb_flake_review_dir=$(mktemp -d)
cp flake.nix flake.lock "$kpb_flake_review_dir/"
nix flake check --no-update-lock-file --print-build-logs "path:$kpb_flake_review_dir"
```

Use that same `path:` reference with an output fragment, such as `#bootstrap-recipe-tools`, for the other commands when reviewing untracked files.

The caller remains responsible for setting the controlled recipe environment and explicitly using the orchestration bundle's CA file for downloads. The bundle does not install trust configuration or set the user's PATH. It also does not replace recipe dependency declarations or their future explicit bootstrap exception mapping.

## Lock management

Normal evaluation, checking, and build commands must use `--no-update-lock-file`. A missing or inconsistent lock is an error, not permission to resolve new inputs. The initial lock was generated by Nix, not constructed from a guessed content hash.

For a deliberate maintainer update, change the full nixpkgs revision in `flake.nix` first, then run `nix flake lock`, review both files, and reevaluate versions and tool checks. Updating a moving channel does not update KPB's fixed input. Commit the definition and lock together through the project's normal review workflow.

## Executed validation and limits

On 2026-11-07, with Nix 2.34.9 on x86_64 Linux:

- Nix parsed the flake, generated the lock, and evaluated all package/check outputs.
- `nix flake check --no-update-lock-file --print-build-logs` passed, building both bundles and the Gawk variant. Its install check and the flake's MPFR check both passed.
- The precision probe distinguished `(2^100)+1` from `2^100`; it also rejected ordinary floating-point arithmetic when run without `-M`.
- The bundle layout check passed, including the CA bundle and recipe/orchestration PATH separation.
- The public `toolVersions` attributes evaluated to the selected version tables.
- A temporary copy without a lock was rejected with `--no-update-lock-file`, and no lock was created.
- The existing lock remained byte-for-byte unchanged during normal validation. The tested temporary flake files matched the workspace files.

Validation used a temporary source containing only the two flake files, without staging or committing changes. No profiles or Nix configuration were changed. This was not a full upstream Gawk test suite, a glibc build, a Bubblewrap confinement test, or a demonstration of Nix-independent runtime. Those remain separate validation work.

The subsequent [Bubblewrap host validation](bootstrap-sandbox.md) now exercises the tools under the required prototype isolation boundary. It is a separate harness, not a recipe executor or proof of a KPB-owned runtime.
